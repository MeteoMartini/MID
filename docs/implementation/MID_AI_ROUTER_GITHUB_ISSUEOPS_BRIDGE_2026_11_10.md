## Tatsächlich implementiert (nur QA)
- `scripts/mid-ai-router-github-issueops.mjs` erstellt in-memory lediglich einen **nicht ausführbaren, ausdrücklich öffentlichen** Einmalreview-Issue-Entwurf. Er verweigert erkennbare Geheimnisse, E-Mails, Mehrfachaufrufe, ungeprüfte Modell-IDs, fehlenden Opt-in und SHA-/Versionsdrift. Es gibt **keinen** echten Providerzugriff oder GitHub-Issue-POST durch dieses Modul.
- Die **separaten** Workflows `.github/workflows/mid-ai-router-groq-issue-relay.yml` und `.github/workflows/mid-ai-router-groq-free-preflight.yml` sowie byteidentische `ci/github/workflows`-Spiegel **existieren im PR #728**. Nach ordentlicher Freigabe könnten sie ein genau kanonisches, vom Repository-Eigentümer erzeugtes öffentliches Katalog-Issue zu einem `mid-stable`-gebundenen **READ-ONLY GET /models** vermitteln. **Heute laufen sie noch nicht auf dem maßgeblichen Stable.**
- Beide Workflows verwenden `concurrency.queue: max` (bei GitHub maximal 100 wartende Läufe); `cancel-in-progress: false` allein schützt bislang nicht davor, dass ein älterer wartender Lauf ersetzt wird. Beide Runner verweigern `GITHUB_RUN_ATTEMPT != 1`; eine manuelle Wiederholung des Jobs sendet weder erneut Dispatch noch eine neue Katalogabfrage. Das ist **kein** globaler Einmalbeweis für eine spätere kostenrelevante Inferenz.
- Keine reale Cloudflare-Verbindung, kein MCP-Ausführungsserver, kein separater Zahlungsplan, keine Providerrechnung und kein authentifizierter Groq-Free-/ZDR-Readback. `mid-ai-router-free-qa` als geschützte GitHub-Environment-Konfiguration und ihr eigens benanntes Environment-Secret `MID_AI_ROUTER_GROQ_FREE_QA_KEY` müssen unabhängig geprüft werden; aus dem Workflow-Text folgt **nicht**, dass sie in GitHub bereits existieren. Weil GitHub ungeschützte Environments implizit erzeugen kann, verlangt der lesende Katalog-Runner zusätzlich die ausdrückliche `MID_AI_ROUTER_GROQ_CATALOG_ARMED=MID-GROQ-CATALOG-QA-V1`-Freischaltung. Ohne diese Variable wird vor einem Provider-GET abgebrochen. Unabhängig muss geprüft werden, dass die Freischaltung sowie der Schlüssel **nur auf Environment-Ebene** liegen; GitHub-Repo-Variablen oder -Secrets mit gleichem Namen wären kein adäquater Nachweis.

## Warum GitHub zuerst prüfen?
`MeteoMartini/MID` ist öffentlich. **Standard-GitHub-hosted Runner** sind in öffentlichen Repositories laut GitHub ohne zusätzliche Runner-Minutenkosten nutzbar; größere oder spezielle Runner sind davon ausgenommen. Der bestehende Runner `ubuntu-24.04` ist Standard. Ein zunächst **rein lesender**, zeitlich begrenzter GitHub-Actions-Check kann daher ohne weiteren Cloudflare- oder Vercel-Dienst fachlich nützlich sein. Der Groq-Free-Tarif verlangt laut Groq eine aktive kostenpflichtige Developer-Umstellung inklusive Zahlungsmethode; das beweist **nicht**, dass der konkrete benutzte Projekt-/Organisationsschlüssel gerade noch Free ist. Groq-ZDR muss für die konkrete Organisation und API-Nutzung gesondert in Data Controls nachgewiesen werden.

## Einmalige echte Inferenz: erst nach gesondertem Sicherheitsdesign
Ein künftiger ChatGPT→GitHub-Issue→Groq-Einmalaufruf ist nur ein **Architekturkandidat**, kein implementierter Feature- oder Kosten-Gate-PASS. Für einen verlässlich idempotenten Auftrag ist neben der Live-Source-/Privacy-/Free-Plan-/Model-Allowlist- und Account-Bestätigung **ein persistenter, global seriell belegter Vorab-Claim** erforderlich. Alle Wiederholungen und mehrdeutigen Providerantworten verbrauchen den Claim dauerhaft. Ein ausschließlich auf GitHub Issues und Workflow-Concurrency basierendes Ledger kann untersucht werden, ist aber erst dann eine Alternative zu SQLite Durable Objects, wenn atomare Claim-Publikation, 429-/Runner-/Rerun-/Cancel-Races, Zustands-Rücklesen, Quota-Subject über Modellschlüssel und Tagesgrenzen, Replays sowie Review-/Signaturtrennung belastbar getestet wurden. `queue: max` allein genügt **nicht**. Andernfalls bleibt der bislang vorgesehene externe atomare Ledger-Pfad verbindlich.

Die Issueinhalte sind öffentlich; keine privaten Unterhaltungen, personenbezogenen Daten, Schlüssel, vertraulichen MID-Quellen oder Wetter-Produktionsdaten übertragen. Echte externe Modellantworten gelten als untrusted und benötigen eigene Originalquellenprüfung, Modellidentität, Usage-/Kostennachweis sowie regulatorisch saubere Abgrenzung von amtlichen Warnungen. Bei fehlenden echten Konto-/Privacy-/Budget-Gates: **STOP**. Keine Übergangslösung mit kostenpflichtigem Provider.
