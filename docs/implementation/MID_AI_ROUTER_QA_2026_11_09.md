## Scope and purpose

The independent router is **not** a MID weather-data endpoint, new user interface,
general-purpose remote shell, or deployment actor. Existing features, RUC,
weather warnings, version mirrors, release pipelines, and Cloudflare Worker
production configuration are deliberately unchanged.

The user requested that ChatGPT coordinate tasks and use a **MID AI Router**
rather than funnel all providers through Kilo. Available execution lanes:

- `github-native`: existing connected GitHub readback — preferred for repository facts.
- `openrouter`: direct, **explicit** model ID ending in `:free`.
- `groq`: direct Free-account API (not any paid developer tier).
- `gemini`: direct Free API-project model, only approved public/redacted inputs.
- Copilot Pro and the already linked Kilo GitHub bot: **existing** bounded
  GitHub-issue/Draft/read-only bridge, not hidden API proxies.
- Work and Codex: ChatGPT-internal, separately quota-limited capacities
  with user-selected modes, **not** callable as arbitrary third-party APIs.
- Replit, Context7, Firecrawl, PostHog, Product Design, Figma, PR Completion:
  task-specific connected tools per existing rules.
- Cubic: optional external GitHub App reviewer, no provider key.
- Vercel AI Gateway, Cloudflare Workers AI: **disabled** pending verified
  free-account billing, hard-stop and privacy scope, not used as paid fallback.

## Actual implementation

`scripts/mid-ai-router.mjs` exports:
- `planMidAiRoute`: pure, deterministic, **network-free** provider choice.
- `buildMidAiRequest`: direct Groq/OpenRouter/Gemini REST payloads
  to fixed HTTPS endpoints. No Kilo forwarding and no user-provided URL.
- `executeMidAiRoute`: **nonproduction** reference request function.
  Live use is blocked unless caller explicitly supplies `liveApproved:true`,
  independent account/price/credit proof, a durable exactly-once claim,
  a server-side credential and trusted transport. No background dispatch
  or retry. Revalidates snapshot and pricing evidence at dispatch time.
- Result classification `UNTRUSTED_REVIEW_ONLY`: never executes
  a model reply, merges a PR or triggers production/release actions.

**No secrets are checked in or read during tests. No external service has
been contacted by this implementation.** Do not publish keys to the weather
frontend, Pages, issues, comments, logs or AI prompts.

### Cryptographic live gate — separately held approver key

`scripts/mid-ai-router-approval.mjs` verifies a **per-request Ed25519
signature** before the router may call any external provider. It uses
Node 22 `crypto.verify(null,...)` and rejects missing/unconfigured keys,
non-Ed25519 keys, malformed signatures, expired/oversized validity periods,
unexpected JSON fields, model/provider/version/source-SHA mismatches and
unsigned changes to the free-tier/privacy evidence fingerprint.

The approver private key is **not** generated by, loaded into, or stored in
the router repository or the execution runtime. Test-only ephemeral keys
are generated in the local Node QA process and are discarded afterward.
The **public** verification key and expected key ID must be provisioned
by a separately trusted operator in a protected server environment:

- `MID_AI_ROUTER_APPROVAL_PUBLIC_KEY_PEM` — pinned Ed25519 public key
- `MID_AI_ROUTER_APPROVAL_KEY_ID` — pinned identifier

The signed grant has a fixed audience
`mid-ai-router-direct-free-review-v1`, versioned canonical field ordering,
strict explicit `maxCostUsd:0` and a **maximum five-minute lifetime**.
At dispatch, server time is read directly from `Date.now()`; callers may
not replace it with a historical timestamp. The grant binds exact
request ID, task kind and content hash, selected provider and model,
SHA, MID version, and the hash of selected Free/pricing/quota/privacy evidence.
It is checked **before** a local claim is consumed or a transport is used.

**Important limitation:** a valid signature means only that the designated
separate approver signed the data. It is **not proof by itself** that a
Free-tier account has a hard zero-cost boundary, that the user owns the
credentials, or that the data are approved for that provider. Only a
future independently audited approval authority that reads live provider
billing and privacy information may issue such grants. Currently no
production approver, private key, public key or environment is configured,
and no live call has been made.

The caller is still a trusted server runtime — this module must never be
used as an internet-exposed arbitrary JSON endpoint. Before any future
production use, the runtime must protect its control-plane environment,
obtain an independently verified GitHub SHA snapshot (not self-reported),
enforce user authorization, use scoped credentials from a safe store,
implement correct durable one-shot admission for its actual deployment,
constrain network egress and log only redacted nonsecret evidence.

Reference: https://nodejs.org/download/release/v22.11.0/docs/api/crypto.html

### Local durable claim ledger — QA boundary only

`scripts/mid-ai-router-ledger.mjs` adds a filesystem-backed, one-use
`makeMidAiLocalDurableClaim({directory,plan})` callback for a *future*
trusted local runner. The callback is compatible with `executeMidAiRoute`'s
`durableClaim` interface but is **never automatically invoked** by MID.

Properties:
- Uses an OS-provisioned, existing **absolute** private (0700) directory
  owned by the current user on a local POSIX filesystem. No default directory,
  no implicit directory creation, no public frontend exposure.
- An `O_CREAT | O_EXCL | O_NOFOLLOW` file reservation prevents two
  local processes from claiming the same request ID. The file and parent
  directory are synced. Records contain no prompt, API key or secret.
- The key is the **request ID alone**, not a combination of provider/model:
  a failed, timed-out or ambiguous call can never be retried automatically
  via another free provider. Even an incomplete claim file stays reserved.
- Stale, malformed, non-private or symlinked directories, non-POSIX systems,
  mismatched plans and filesystem failures **block** execution.
- **Not approved for NFS, ephemeral GitHub runners, distributed Workers,
  multi-host execution or production.** The exclusivity guarantee may not
  hold on network filesystems; the reference implementation does not
  prove host/volume permanence, crash fsync guarantees of underlying media
  or account spending constraints. A production shared store would need
  its own atomically conditional write, durable readback and recovery audit.

Offline QA: `node scripts/qa-mid-ai-router-ledger-0985452.mjs`.
`tests/unit/mid-ai-router.test.ts` also runs this suite via the
existing Node 22 Vitest pilot. The QA tests include 24 concurrent contenders,
process-restart replay, symlink and permission checks, invalid request IDs,
truncated/crashed reservation and metadata privacy. This is a safe local
countermeasure, **not a completed production secret/dispatch host**.

## Router credentials (future controlled environment only)

When independently checked and authorized, the backend will read:

| Provider | Intended environment secret | Where |
| --- | --- | --- |
| Groq Free | `GROQ_API_KEY` | Dedicated protected MID AI Router backend environment |
| OpenRouter :free | `OPENROUTER_API_KEY` | Same environment |
| Gemini Free | `GEMINI_API_KEY` | Same environment |

These values **do not** belong in Kilo BYOK for MID routing. Kilo may
independently use the user's existing setup for its own authorized work,
but is not the router's proxy. No repository/environment secrets should
be created before scope and a safe backend are finalized. Account creation,
OAuth and billing remain user actions.

### Free proof is not a self-service toggle

`planMidAiRoute` accepts a provider registry from a **trusted
external control plane**; it cannot independently determine the user's
real account billing status or guarantee that a remote provider will never
bill. For every call, a future audited control plane must fetch/revalidate:

- Account actually in Free tier; upgrades/credits/auto-top-up disabled,
  no postpaid metering or paid fallback; a genuine provider-side hard stop.
- Price for that **exact** model, both input and output = USD 0, evidence
  from an official source; free-pricing proof newer than six hours.
- Account-specific remaining requests and rate limits; cap exhaustion
  blocks routing. The requested exact model must have independently verified
  current Free-tier availability (`modelAvailabilityVerified`).
- Privacy terms, prompt redaction, request scope and retention. The control
  plane supplies explicit `privacyApproved` and fresh `privacyCheckedAt`
  only after the data-use rules were independently reviewed; Gemini Free
  may use prompts for product improvement, so private/unreleased MID data
  remain excluded. OpenRouter requests additionally set `data_collection:deny`,
  `zdr:true`, `max_price:{prompt:0,completion:0,request:0}` and
  `allow_fallbacks:false`; incompatibility is a deliberate no-result, not a
  reason to relax privacy or cost filters. Groq uses `max_completion_tokens`.
- Stable+main exact SHA and version, user-initiated task ID and
  **durable exactly-once dispatch**. A simple volatile in-memory Set
  is insufficient. No automatic retry after ambiguous response.

**Do not set the proof flags solely because an API key exists, a model name
says "free", or a generic console has a soft budget.** Production HTTP
dispatch must remain disabled until the above server-side evidence/secret
manager/idempotency components are separately implemented and verified.
The reference `executeMidAiRoute` is NOT a release-grade
permission gateway.

The `tests/unit/mid-ai-router.test.ts` Vitest test runs both offline QA

limits, malformed UTF-8 and invalid/missing HTTP body/length handling.
The additional local filesystem-ledger QA covers the same-request provider

are checked exactly (Gemini may use a `models/` prefix); missing or

provider model from being labeled as the approved model, but cannot
recover free quota spent by an already completed request. See the
[Groq API reference](https://console.groq.com/docs/api-reference),
[OpenRouter Chat Completions](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request)
and [Google GenerateContentResponse](https://ai.google.dev/api/generate-content).

### MID AI Router 1.1 · konservative Publisher-Provenienz (09.11.2026, QA Draft)

Auf Draft #728 wird ein Grenzfall des früheren `family(p)`-Heuristikcodes behoben: Die Groq-ID `llama-3.3-70b-versatile` und eine OpenRouter-ID `meta-llama/…:free` dürfen **keine unabhängigen Foundation-Familien** nur aufgrund abweichender Namespace-Präfixe darstellen. OpenRouter-IDs im Test sind synthetische Offline-Fixtures, **keine geprüfte Free-Modellverfügbarkeit**.

Für den ausdrücklich genehmigten Zwei-Request-Plan wird jetzt ein vom unabhängigen Attester auf Originalanbieter-/Modellmetadaten geprüfter kanonischer `foundationPublisher` verlangt, mit `lineageVerified=true`, frischem `lineageCheckedAt` und `lineageEvidenceSha256`. Alle vier Felder werden in `proofFingerprint` gebunden und damit durch die bereits vorhandene Ed25519-Ausführungsfreigabe SHA-/Request-/Plan-gebunden. Der Router prüft bekannte Modellnamespace-/Alias-Zuordnungen zusätzlich konservativ; unbekannte oder widersprüchliche Namespaces, fehlende oder abgelaufene Evidenz blockieren den Blend. Eine synthetische Mock-Attestierung ist **kein echter Provenienzbeleg** und ermöglicht ohne unabhängige Signierinstanz keinen Live-Dispatch.

Sieben zusätzliche reine Offline-Regressionsfälle (insgesamt 27 Blend-Szenarien) prüfen Groq-Llama↔OpenRouter-Meta-Llama, widersprüchliche Herkunftsangaben, fehlenden Echtheitsmarker, unbekannte Aliasse, fehlenden Digest, veraltete Provenienz und Signatur-Hash-Bindung. Die drei direkten Provider-Adapter bleiben unverändert, kein Kilo-/Copilot-Doppelauftrag, keine kostenpflichtige Modellanfrage, keine Secret- oder Release-Änderung.


### MID AI Router 1.1 – temporärer SHA-Readback direkt vor Dispatch (09.11.2026)

Auch mit einem signierten Auftrag darf der Executor nicht bloß einen übergebenen, potenziell veralteten oder erfundenen `snapshot` akzeptieren. Vor Plan-Erneuerung, Ed25519-Prüfung, dauerhaftem Ledger-Claim oder Modellnetzwerkaufruf ist daher ein **unabhängiger, höchstens 30 Sekunden alter** `trustedSourceReadback` des vertrauenswürdigen Server-Runners verpflichtend. Verglichen werden `mainSha`, `stableSha`, Version und der vom Nutzer autorisierte SHA. Fehlender/fehlerhafter/veralteter Callback, Main-/Stable-Drift oder Versionsdrift blockiert ohne Modellrequest oder Reservierung. Die eigenständige Vertrauenswürdigkeit des GitHub-API-Readbacks muss der spätere geschützte Runner sicherstellen; ein beliebiger Callback allein ist **kein** nachgewiesener Original-SHA. Zudem wird fehlendes Provider-Usage nie als 0 behandelt: `usageStatus=NOT_VERIFIED` und `costStatus=NOT_VERIFIED`, auch bei erfolgreichem Mock-Response.

Sieben zusätzliche negative Direkt-Router-Fälle, insgesamt 81 Direkt-, 15 Ledger- und 27 Blend-Offline-Fälle; kein echter Provider-/Vercel-Request, keine Schlüssel-/Release-/Wetter-/CI-Änderung. Die neue Vercel-Teamverbindung `mid-e1e0` liefert beim Connector-Project-Read `403 forbidden` und benötigt die von Vercel selbst bereitgestellte, einmalige Teamfreigabe. Bis Konto-/Guthaben-/Hard-Cash-/Signer-/Store-Nachweis weiterhin **LIVE BLOCKED**.


### MID AI Router 1.1 – GitHub-Original-Lesebaustein (09.11.2026)

`scripts/mid-ai-router-github-readback.mjs` ist ein isolierter, nicht produktiv aktivierter Server-Helper: Zwei **aktuelle** fest verdrahtete GitHub-Refs `main` und `mid-stable` werden mit fehlertoleranzfreiem, begrenztem HTTPS-GET gelesen. Erst bei identischem gültigem 40-Zeichen-SHA werden `package.json`, `MID_BASELINE.json` und `contracts/index.json` **SHA-gepinnt** aus GitHub Raw gelesen. Nur vollständig übereinstimmende Versionsspiegel liefern einen zeitgestempelten `trustedSourceReadback` für den Direct-Executor. Alle Requests sind Credential-frei, fest auf GitHub-Domains/Dateipfade beschränkt, ohne Redirects/Cache, zeit- und bytebegrenzt. Fehlende API-/Version-/Bytes-/JSON-/TLS-/Datengültigkeits-Evidenz blockiert.

`scripts/qa-mid-ai-router-github-readback-0985452.mjs` enthält 14 vollständige Offline-Mock-Szenarien mit Fake-Fetch, darunter SHA-/Version-/Transport-/HTTP-/Byte-/UTF8-Fehler. Der neue Runner wird über Vitest/Node22 ausgeführt. **Keine reale GitHub- oder Provider-Anfrage im Testlauf** und weiterhin kein geschützter, autorisierter 24/7-Executor, keine Produktivfreigabe. Der geschützte spätere Server muss den Helper selbst verwenden; die öffentlich importierbare Callback-Signatur alleine stellt keine vertrauenswürdige Serveridentität her.
