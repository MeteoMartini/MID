## Zielweg – strikt sequenziell, niemals Gate-Bypass

1. **Nur eine fachlich überprüfte Quelländerung** auf `main`: bereits vorhandener exakter Source-PR-Gate + SHA-/Review-Readback, später GitHub-native PR-/Stale-Approval-/Thread-Sperre mit **keiner** neuen Umgehungsberechtigung. Ein berechtigter, vom Autor unabhängiger GitHub-Reviewer bleibt zwingend; Reviewtexte allein sind keine Codeabnahme.
2. **Serverseitiges ZIP bleibt**: bestehender #839 Git-Tree-Builder erzeugt es aus dem kontrolliert gemergten SHA; statt ZIP-only-Push auf main sichere, einzig zuordenbare Actions-Artefakt-ID, Run-/Attempt-/Repository-/Workflow-SHA und Digest. Der Installer verifiziert die originale Git-Tree-Inventur und ZIP-Envelope vor **sämtlichen unveränderten** Core-/Heavy-/DWD-/RUC-/Security-/Worker-/Pages-Gates.
3. **Installer baut dist unabhängig und deployt über Pages-Artefakt**, nicht durch einen zweiten Git-Push auf main. Dauerhafte Web-Recovery wird über GitHub Release **nach** erfolgreichem Installer/Worker/Pages-Fencing und zunächst als Shadow-Doppelarchiv gewährleistet: `MID-professional-replacement.zip`, `MID-dist-release.zip`, `MID-release-manifest.json` (Version, Source-SHA, exakte Build-Eingabefingerprints, Asset-Hashes, Run-/Attempt-IDs, PWA-/Widget-/RUC-Vertragsstatus). Erst draft + alle Assets hochladen, dann mit aktivierter Release-Immutability endgültig veröffentlichen; zu diesem Zeitpunkt muss der Tag auf den freigegebenen SHA zeigen. Kein temporärer unveränderlicher Release als produktives Rollback vor erfolgreicher Qualifikation.
4. **Manuellen `deploy.yml`-Fallback vor Abschaltung des alten dist-Commits migrieren**: Der heutige Workflow verlangt dreimal `mid-stable:dist/index.html`. Neuer Pfad muss `main=mid-stable=tag-SHA` und Release-immutability bestätigen, JSON-/Release-Attestation/Download-Inventar authentifizieren, ZIP-Bytes und Dateisicherheit prüfen, `dist/index.html`, RUC-/Same-Origin-/PWA-/Widget-/iOS-Recovery nachweislich erhalten und die originale Pages-Serialisierung/Freshness respektieren. Bei fehlendem Release oder altem Bestand fail-closed auf das bisherige unveränderte Stable-Recovery, **kein** stiller Wechsel.
5. **Phasenfreigabe:** (a) read-only Metadatenpilot + adversariale Tests → (b) separater authentifizierter GitHub-Shadow-Release-/Recovery-Pilot auf isoliertem nicht produktivem Ref mit echten Binärbytes/Attestation, Rollback und Kostenprüfung → (c) beide Main-Pushes ausschließlich zusammen abschalten, Source/Installer inklusive E2E testen → (d) Owner aktiviert native Review-/No-Bypass-Regel **erst nachdem** die komplette Kette nachweislich kompatibel ist → (e) adversariale echte späte `CHANGES_REQUESTED`-/COMMENTED-P1-/SHA-Race-Gegenversuche + reguläre Gates → (f) erfolgreiche Stable-Promotion. Keine doppelte native Freigabeschranke oder Replit-/Copilot-Produktionsarbeit.
6. **Rückabwicklung:** Unveränderte alte Workflow- und Installer-Verträge bleiben bis Shadow-/Rollback-Gates erfolgreich; ein GitHub Release ersetzt weder den echten Browser-/Pages-Test noch die RUC-Publisher-/PWA-Integritätsprüfung. Ohne gleichwertiges dauerhaftes Archiv ist die Entfernung des zweiten Main-Pushs verboten. Etwaige Aktivierung der neuen GitHub Release-Immutability ist ein späterer expliziter Owner-Schritt; bestehende alte Tags/Releases werden dadurch nicht rückwirkend attestiert.

## GitHub-native Merge-Optionen: tatsächliche Verfügbarkeit im MID-Repository

Am 16.11.2026 live aus der GitHub-Repo-API geprüft: `MeteoMartini/MID` ist ein **öffentliches, nutzergeführtes Repository** (`owner.type=User`); `allow_auto_merge=false`, `allow_squash_merge=true`. GitHubs Merge Queue ist laut offizieller Dokumentation nur für geeignete **organisationsgeführte** Repositories verfügbar und ist deshalb **kein** pragmatischer MID-Cutover ohne Repository-Umzug. Eine solche Migration gehört nicht zu diesem Auftrag. Quelle: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue .

**Normaler GitHub Auto-Merge** ist grundsätzlich auch für öffentliches User-Repository verfügbar, derzeit aber ausdrücklich deaktiviert; GitHub aktiviert Merge erst nach Erfüllung aller native Reviews/Statuschecks. Quelle: https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request . Dies kann nach einem erfolgreichen Source-/Artifact-Cutover die bisherige privilegierte Bot-Merge-Entscheidung zusätzlich vereinfachen und den Privileg-Übergang der Source-Release-`workflow_run`-Kette reduzieren. **Aber:** Es löst weder ein nur als `COMMENTED` abgegebenes berechtigtes P1 von selbst noch den verbleibenden Self-Heal-`workflow_run`-High-Befund. Hierfür weiterhin unabhängige SHA-gebundene Befunddisposition und GitHub-native Reviewer-/Stale-Review-Regeln verlangen.

**Nicht vorzeitig aktivieren:** Ohne die vollständig qualifizierte Doppeltransport-/Recovery-Kette, authentifizierten Schutzregel- und Original-GitHub-Negativtests kann der heutige ZIP-/Installer-Push bei einer neuen verpflichtenden PR-Regel blockieren. Das bestehende `allow_auto_merge=false` wird durch diesen QA-Entwurf nicht verändert. Spätere einmalige Owner-Entscheidungen über Auto-Merge und Release-Immutability erst nach isoliertem Shadow-Pilot, ohne neuen Token oder Bypass. Ein unabhängiger Reviewer pro tatsächlichem produktiven Quell-PR kann Zeitkosten verursachen; reale Releasezeit/Actions-Minuten müssen gegenüber dem bestehenden Prozess gemessen werden, nicht behauptet.

## MID Release Konzept 1.5 · Native Review vs. LEGACY `main`-Writes: originaler GitHub Ruleset-/Git-Blob-Readback (16.11.2026, NO RELEASE)

**Sicherheitsgrenze:** Eine wirklich verpflichtende GitHub-Reviewregel für `main` darf nicht dadurch umgangen werden, dass der privilegierte Release-Bot eine dauerhafte `always`-Ausnahme behält; eine No-Bypass-Regel dagegen kollidiert voraussichtlich mit den bisher direkt nach `main` geschriebenen `MID-professional-replacement.zip`- und Installer-/Self-Heal-Commits. **Neuer sicherer GitHub-Live-Pilot:** `tools/ci/mid-740-native-review-cutover-readback.mjs` prüft unabhängig und ausschließlich **lesend** die Repo-ID `1305110795`, `main=mid-stable=a78465b655d25cafc9ecc0390080694cb7aca957`, das vollständige aktive Inventar von fünf Original-Rulesets, ihre einzelnen GitHub-REST-Detailobjekte samt `MID Production Branch Guard` (`23963851`), dessen `Integration:5059236/always`-Bypass, `MID Stable Protection` (`21919727`) mit `MID / release-candidate-quality` und den fehlenden `pull_request`-Typ **in diesem konkreten Ruleset**. **Grenze der Sichtbarkeit:** Die zusätzliche klassische Branchschutz-REST-API antwortete der verbundenen Integration zuletzt mit `403 Resource not accessible by integration`; sie wird daher separat abgefragt und bei Fehlern explizit `UNVERIFIED` notiert. Statt für die QA breit privilegierte Tokens einzuführen oder bestehende Rulesets zu lockern, verlangt der native Review-Cutover-Readback jetzt einen von zwei **ausdrücklich nicht autorisierenden** Originalzuständen: (a) alle Bypass-Akteure sind im tatsächlich lesenden Kontext sichtbar und entsprechen der bereits belegten Legacy-Konfiguration, oder (b) **alle** Bypass-Akteure sind redigiert, Status `BYPASS_ACTORS_UNVERIFIED_CUTOVER_BLOCKED_QA_ONLY`, `rulesetBypassActorsVerified:false`, `productionReleaseIntegrationAlwaysBypasses:null`. Teilsichtbarkeit oder sonstige Policy-Drift blockiert vollständig.
